# P1-2.2 테이블별 RLS 매트릭스 + 적용 순서

본 문서는 Task `10000000-0000-4000-8000-000000000047`의 산출물이다.  
목표는 서비스 전환 핵심 12개 테이블에 대해 RLS CRUD 권한 매트릭스를 확정하고, 실제 Supabase 상태를 반영한 안전한 적용 순서를 정의하는 것이다.

## 1) 실DB 기준 베이스라인 (Supabase MCP 측정)

- 측정일: `2026-03-02` (KST)
- 프로젝트: `vjmerqaxguovnojinxfq` (`every-shift-mvp`)
- 확인 결과:
  - RLS 활성화: `schedules`, `schedule_preferences`만 활성
  - 기존 정책: 다수 `USING true / WITH CHECK true` 형태(테넌트 격리 보장 불가)
  - 헬퍼 함수 부재: `public.is_super_admin`, `public.has_org_access` 미존재

## 3) 공통 인터페이스/정책 기준

### 3.1 Public DB Interface

- `public.is_super_admin() -> boolean`
- `public.has_org_access(target_org_id uuid, min_role text default 'user') -> boolean`

### 3.2 공통 권한 원칙

1. `super` + `account_status='active'`는 전역 우회 허용.
2. 그 외는 `account_status='active'` + `organization_memberships.status='approved'` 필요.
3. 최소 역할:
   - `min_role='admin'`: org admin만 허용
   - `min_role='user'`: org admin/user 허용
4. 기본 전제:
   - 인증 사용자만 대상(anon 미허용)
   - 조직 생성/승인 일부는 Edge Function(service role) 경유 허용 가능
   - soft-delete보다 상태 전이(`status`) 우선

## 4) 핵심 12개 CRUD 매트릭스 (결정본)

표기: `S=SELECT`, `I=INSERT`, `U=UPDATE`, `D=DELETE`

| Table | super | admin | user | 스코프/조건 |
| :--- | :--- | :--- | :--- | :--- |
| `profiles` | `S/I/U/D` 전체 | `S/I/U` self, `D` 금지 | `S/I/U` self, `D` 금지 | `id = auth.uid()` self 정책 + super 우회 |
| `organization_memberships` | `S/I/U/D` 전체 | `S/I/U` 자기 조직, `D` 금지 | `S` self만, `I/U/D` 금지 | admin은 조직 승인/상태 관리, user는 본인 상태 조회만 |
| `organizations` | `S/I/U/D` 전체 | `S/U` 자기 조직, `I/D` 금지 | `S` 자기 조직, `I/U/D` 금지 | org root 엔티티 |
| `signup_requests` | `S/I/U/D` 전체 | `S/U` 자기 조직 심사 + self `I/S/U`, `D` 금지 | self `I/S/U`, `D` 금지 | `organization_id is null` self 요청 허용 필요 |
| `employees` | `S/I/U/D` 전체 | `S/I/U/D` 자기 조직 | `S/U` self row, `I/D` 금지 | self 기준은 `employees.user_id = auth.uid()` |
| `schedules` | `S/I/U/D` 전체 | `S/I/U/D` 자기 조직 | `S` 자기 조직, `I/U/D` 금지 | 기존 permissive 정책 교체 대상 |
| `shifts` | `S/I/U/D` 전체 | `S/I/U/D` 자기 조직 | `S` 자기 조직, `I/U/D` 금지 | 조직 마스터 |
| `sites` | `S/I/U/D` 전체 | `S/I/U/D` 자기 조직 | `S` 자기 조직, `I/U/D` 금지 | 조직 마스터 |
| `skills` | `S/I/U/D` 전체 | `S/I/U/D` 자기 조직 | `S` 자기 조직, `I/U/D` 금지 | 조직 마스터 |
| `ranks` | `S/I/U/D` 전체 | `S/I/U/D` 자기 조직 | `S` 자기 조직, `I/U/D` 금지 | 조직 마스터 |
| `schedule_assignments` | `S/I/U/D` 전체 | `S/I/U/D` 자기 조직 | `S` self assignment만, `I/U/D` 금지 | 간접 스코프(`schedules.organization_id` 조인 기준) |
| `site_requirements` | `S/I/U/D` 전체 | `S/I/U/D` 자기 조직 | `S` 자기 조직, `I/U/D` 금지 | legacy + 확장 필드 공존 |

## 5) 정책 클래스 분류 (SQL 구현 시 재사용 단위)

1. Self-owned 클래스: `profiles`
2. Org direct 클래스: `organizations`, `employees`, `schedules`, `shifts`, `sites`, `skills`, `ranks`, `site_requirements`
3. Membership workflow 클래스: `organization_memberships`, `signup_requests`
4. Org indirect 클래스: `schedule_assignments` (조인/exists 필요)

## 6) 적용 순서 (Rollout Order)

1. 헬퍼 함수 생성/검증: `is_super_admin`, `has_org_access`
2. Identity 기반: `profiles`, `organization_memberships`
3. 조직 루트: `organizations`
4. 조직 마스터: `shifts`, `sites`, `skills`, `ranks`
5. 운영 테이블: `employees`, `schedules`, `site_requirements`
6. 간접 참조: `schedule_assignments`
7. 기존 permissive 정책 정리: `schedules`의 `true` 정책 제거/교체
8. 부록 테이블 보강: `schedule_preferences` permissive 정책 제거/교체

## 7) 단계별 적용 체크포인트

### 7.1 사전 체크

- 헬퍼 함수 존재 여부 확인
- 기존 정책 백업(`pg_policies` 스냅샷)
- 영향 테이블 row count 확인

### 7.2 단계 적용 시 공통 검증

- 허용 경로: super/admin/user 정상 케이스 1개 이상
- 차단 경로: cross-tenant 1개 이상
- 비활성 계정 차단: `account_status != 'active'`

### 7.3 정책 교체 시 주의

- `DROP POLICY` 전에 동일 cmd 대체 정책 생성 순서 유지
- `schedule_assignments`는 조인 누락 시 IDOR 위험이 높아 마지막 단계 적용

## 8) P1-2.3 인계용 검증 시나리오

1. super가 타조직 데이터 `S/I/U/D` 가능
2. admin이 타조직 `SELECT` 포함 전면 차단
3. user는 자기 assignment만 조회, 타직원 assignment 차단
4. `account_status != active` 계정 전면 차단
5. membership `pending/rejected/withdrawn` 차단
6. `schedule_assignments` 조인 누락(IDOR) 방지 검증
7. `signup_requests`에서 `organization_id is null` self-create/self-withdraw 허용 + 타인 수정 차단
8. `schedules`, `schedule_preferences` permissive 정책 제거 후 회귀 없음

## 9) 드리프트 기록 (중요)

- `migrations/008_rls_progressive_rollout.sql`의 기대 상태와 실제 DB 상태가 일치하지 않음.
- 본 문서는 migration 파일이 아니라 **실DB 측정 결과**를 기준으로 적용 순서를 정의함.

## 10) 비범위(Out of Scope)

- 본 태스크에서 실제 SQL 적용/배포는 수행하지 않음.
- 본 태스크 산출물은 RLS 정책 매트릭스와 적용 순서 결정 문서임.
