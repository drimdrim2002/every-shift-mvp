# Phase2A-2 Go-Live Ops UI 테스트 케이스

이 문서는 제3자 수동 QA 담당자가 브라우저 UI만 보고 그대로 따라 할 수 있도록 정리한 문서다. 내부 운영/API 검증은 이 문서 범위에서 제외하고 `scripts/ops/run-phase2a-go-live-ops-checks.sh`로 자동 실행한다.

## 1. 개요

### 1.1 문서 목적

- 제3자 테스트 담당자가 화면에서 실제로 보이는 문구와 버튼 기준으로 테스트할 수 있게 한다.
- 운영 파일럿 시작 전에 현장 관리자가 겪는 준비 흐름과 생성 흐름을 확인한다.
- 내부 구현 이름이나 API 경로를 몰라도 테스트를 진행할 수 있게 한다.

### 1.2 이 문서에서 자주 쓰는 용어

| 용어                 | 쉬운 설명                                                               |
| -------------------- | ----------------------------------------------------------------------- |
| 현장 관리자          | 실제 조직에서 운영 파일럿을 진행하는 관리자 사용자                      |
| 운영 준비            | 근무표를 만들기 전에 조직, 사이트, 직원, Off 기준을 먼저 맞추는 단계    |
| 운영 준비 체크리스트 | 대시보드에서 준비 상태와 바로가기 링크를 보여주는 카드                  |
| 스케줄 대상 사이트   | 현재 조직에서 기준으로 삼는 대표 사이트                                 |
| 초기 데이터 입력     | Step4에서 직원별 Off/O 제약과 메모를 입력하는 단계                      |
| 결과 확인            | Step5에서 배정표, 하드 제약, Off 요청, 공정성 요약을 읽고 확인하는 단계 |
| 읽기 전용 상태       | 화면은 볼 수 있지만 수정이나 재실행을 할 수 없는 상태                   |

### 1.3 이번 문서에서 검증하는 범위

- O1: 대시보드의 운영 준비 카드와 체크리스트 노출
- O2: 조직/사이트 기본 설정 화면의 저장과 재조회
- O3: 운영 준비용 Step2와 Step3의 저장, 재진입, 안내 문구
- O4: 월별 근무표 생성 흐름의 Step2, Step3, Step4 이동과 저장
- O5: Off 사용 기준 설정 화면의 저장과 재진입 UX
- O6: Step5 결과 확인 화면의 탭 전환, 경고 요약, 읽기 전용 상태

### 1.4 이번 문서에서 다루지 않는 범위

- 내부 운영자용 `bootstrap-admin` 실행
- `profiles`, `onboarding_progress`, Auth metadata 직접 확인
- CORS preflight, 허용 메서드, 직접 API 호출
- RPC 호출 여부, DB row 직접 조회, atomic replace 확인
- fairness ledger write 여부와 finalize 내부 구현 확인
- 조직 범위 차단, operator 권한, bootstrap 권한 분리 같은 내부 권한 검증

### 1.5 수동 QA와 내부 자동 검증의 경계

- 제3자 수동 QA는 브라우저 UI만 사용한다.
- 제3자 수동 QA는 SQL Editor, DevTools network payload, curl, Edge Function 직접 호출을 사용하지 않는다.
- 내부 운영/API 검증은 아래 스크립트로 실행한다.

```bash
./scripts/ops/run-phase2a-go-live-ops-checks.sh
```

## 2. 사전 조건

### 2.1 계정과 데이터 준비

- 현장 관리자 계정이 준비되어 있어야 한다.
- 테스트 담당자는 브라우저 로그인만 가능하면 된다.
- 대상 조직에는 아래 데이터가 준비되어 있어야 한다.
  - 조직 정보 1건
  - 사이트 데이터 1건 이상
  - `shifts`와 Step2 표시용 시프트 기준 데이터
  - Step3 테스트용 직원 예시 데이터 또는 업로드 가능한 엑셀 파일
  - Off 사용 기준 확인용 기본 정책과 직급별 정책 예시
  - Step5 검토용 스케줄 1건 이상
  - 최종 확정되어 읽기 전용으로 볼 수 있는 월 1건 이상

### 2.2 브라우저 기반 수동 QA 환경

- 앱이 실행 중이어야 한다.
- 테스트 담당자는 로그인 가능한 계정을 받아야 한다.
- 제3자 테스트 담당자는 브라우저 UI 외 도구를 사용하지 않는다.

### 2.3 테스트에 필요한 화면

- 대시보드(`/`)
- 조직/사이트 기본 설정(`/ops/organization-setup`)
- Off 사용 기준 설정(`/ops/off-request-policy-setup`)
- 운영 준비용 Step2: 대시보드 체크리스트의 `사이트/근무 기본 설정`
- 운영 준비용 Step3: 대시보드 체크리스트의 `직원 로스터 준비`
- 월별 생성 흐름 Step1 기본 정보(`/schedule/step1`)
- 월별 생성 흐름 Step2 요일별 인력 설정(`/schedule/step2`)
- 월별 생성 흐름 Step3 직원 정보 입력(`/schedule/step3`)
- 월별 생성 흐름 Step4 초기 데이터 입력(`/schedule/step4`)
- Step5 결과 확인(`/schedule/step5/:scheduleId`)

### 2.4 내부 자동 검증 실행용 환경

다음 항목은 제3자 수동 QA가 아니라 세션 자동 검증에서만 사용한다.

- 기본 실행:
  - `pnpm install`
- 브라우저 smoke까지 함께 돌릴 때:
  - `.env.test`
  - `TEST_USER_EMAIL`
  - `TEST_USER_PASSWORD`
- finalized read-only까지 함께 돌릴 때:
  - `TEST_FINALIZED_MONTH`
- live bootstrap smoke까지 함께 돌릴 때:
  - `SUPABASE_URL`
  - `PHASE2_OPS_OPERATOR_ACCESS_TOKEN`
  - `PHASE2_OPS_BOOTSTRAP_ORGANIZATION_ID`
  - `PHASE2_OPS_BOOTSTRAP_TARGET_EMAIL`
  - `PHASE2_OPS_BOOTSTRAP_DISPLAY_NAME`

## 3. 정상 흐름 UI 테스트 케이스

### TC-UI-01: 대시보드에서 운영 준비 상태를 본다

- ID: TC-UI-01
- 목적: 현장 관리자가 로그인 후 대시보드에서 운영 준비 카드와 체크리스트를 볼 수 있는지 확인한다.
- 사전 조건: 로그인 가능한 현장 관리자 계정이 있다.
- 테스트 단계:
  1. 로그인 후 대시보드로 이동한다.
  2. 상단 제목이 `근무표 관리`인지 확인한다.
  3. `운영 준비` 영역이 보이는지 확인한다.
  4. `조직/사이트 기본 설정이 완료되었습니다` 또는 `조직/사이트 기본 설정이 아직 완료되지 않았습니다` 카드가 보이는지 확인한다.
  5. `운영 준비 체크리스트` 카드가 보이는지 확인한다.
- 기대 결과:
  - 대시보드 상단에서 운영 준비 상태를 바로 이해할 수 있다.
  - 체크리스트 카드 안에 준비 단계별 제목이 보인다.
  - 내부 운영자 전용 bootstrap 버튼이나 링크는 브라우저 UI에 노출되지 않는다.
- 관련 자동화 테스트:
  - `tests/unit/dashboard.spec.ts`
  - `tests/e2e/pilot-checklist.spec.ts`

### TC-UI-02: 체크리스트 링크로 각 준비 화면에 이동한다

- ID: TC-UI-02
- 목적: 대시보드 체크리스트에서 각 준비 화면으로 바로 이동할 수 있는지 확인한다.
- 사전 조건: `운영 준비 체크리스트` 카드가 보인다.
- 테스트 단계:
  1. `조직 기본 정보 확인`의 `열기`를 누른다.
  2. 다시 대시보드로 돌아온다.
  3. `사이트/근무 기본 설정`의 `열기`를 누른다.
  4. 다시 대시보드로 돌아온다.
  5. `직원 로스터 준비`의 `열기`를 누른다.
  6. 다시 대시보드로 돌아온다.
  7. `Off 사용 기준 설정`의 `열기`를 누른다.
  8. 다시 대시보드로 돌아온다.
  9. `최종 검토 진입`의 `열기`를 누른다.
- 기대 결과:
  - 각 링크가 해당 화면으로 이동한다.
  - 이동 후 화면 제목이나 주요 카드 제목이 현재 단계와 맞는다.
  - 사용자는 대시보드에서 바로 다음 작업으로 들어갈 수 있다.
- 관련 자동화 테스트:
  - `tests/e2e/pilot-checklist.spec.ts`

### TC-UI-03: 조직 기본 정보를 저장하고 다시 열어도 유지된다

- ID: TC-UI-03
- 목적: 조직명과 조직 유형을 저장한 뒤 다시 열었을 때 값이 유지되는지 확인한다.
- 사전 조건: `조직/사이트 기본 설정` 화면에 접근 가능하다.
- 테스트 단계:
  1. `조직 기본 정보` 영역에서 조직명을 입력한다.
  2. 조직 유형을 입력한다.
  3. 저장 버튼을 누른다.
  4. 성공 메시지를 확인한다.
  5. 페이지를 새로고침한다.
- 기대 결과:
  - 저장 성공 메시지가 표시된다.
  - 새로고침 후에도 저장한 조직명과 조직 유형이 그대로 보인다.
  - 이후 대시보드에서도 같은 조직 기준을 사용하는 흐름으로 이해된다.
- 관련 자동화 테스트:
  - `tests/unit/phase2-ops-api.spec.ts`
  - `tests/unit/dashboard.spec.ts`

### TC-UI-04: 대표 사이트를 지정하고 다시 열어도 유지된다

- ID: TC-UI-04
- 목적: 조직/사이트 기본 설정에서 대표 사이트를 저장하고 다시 열어도 같은 사이트가 유지되는지 확인한다.
- 사전 조건: `조직/사이트 기본 설정` 화면에 접근 가능하다.
- 테스트 단계:
  1. 사이트 정보를 입력하거나 수정한다.
  2. 스케줄 대상 사이트로 사용할 사이트를 선택한다.
  3. 저장 버튼을 누른다.
  4. 성공 메시지를 확인한다.
  5. 페이지를 새로고침한다.
- 기대 결과:
  - 저장 성공 메시지가 표시된다.
  - 다시 열었을 때 대표 사이트가 그대로 보인다.
  - 이후 Step2와 대시보드에서 같은 대표 사이트를 기준으로 안내한다.
- 관련 자동화 테스트:
  - `tests/unit/phase2-ops-api.spec.ts`

### TC-UI-05: 운영 준비용 Step2에서 사이트 기준을 저장한다

- ID: TC-UI-05
- 목적: 대시보드 체크리스트에서 연 Step2가 운영 준비 화면으로 보이고 저장이 가능한지 확인한다.
- 사전 조건: 대표 사이트가 저장되어 있고 대시보드 체크리스트에서 Step2로 들어갈 수 있다.
- 테스트 단계:
  1. 대시보드 체크리스트의 `사이트/근무 기본 설정`으로 들어간다.
  2. 상단 제목이 운영 준비용 안내로 보이는지 확인한다.
  3. `현재 스케줄 대상 사이트` 안내 문구가 보이는지 확인한다.
  4. 월요일 또는 화요일 필요 인력 값을 수정한다.
  5. `저장`을 누른다.
  6. 성공 메시지를 확인한 뒤 대시보드로 돌아간다.
  7. 다시 같은 화면으로 들어와 저장값을 확인한다.
- 기대 결과:
  - 이 화면이 월별 생성이 아니라 조직 공통 기준을 다루는 화면으로 이해된다.
  - 대표 사이트 안내 문구가 보인다.
  - 저장 후 다시 열었을 때 수정한 값이 유지된다.
- 관련 자동화 테스트:
  - `tests/unit/step2-site-info.spec.ts`
  - `tests/e2e/pilot-checklist.spec.ts`

### TC-UI-06: 운영 준비용 Step3에서 직원 기준을 저장한다

- ID: TC-UI-06
- 목적: 대시보드 체크리스트에서 연 Step3가 운영 준비 화면으로 보이고 직원 기준 저장이 가능한지 확인한다.
- 사전 조건: 대시보드 체크리스트에서 Step3로 들어갈 수 있고 직원 예시 데이터나 업로드 파일이 있다.
- 테스트 단계:
  1. 대시보드 체크리스트의 `직원 로스터 준비`로 들어간다.
  2. 상단 제목이 운영 준비용 직원 화면인지 확인한다.
  3. `직접 입력` 또는 `엑셀 업로드` 중 하나로 직원을 입력한다.
  4. 직원 목록이 화면에 보이는지 확인한다.
  5. `저장`을 누른다.
  6. 저장 확인 대화상자가 뜨면 내용을 읽고 저장을 진행한다.
  7. 성공 메시지를 확인한다.
  8. 대시보드로 돌아갔다가 다시 열어 저장값을 확인한다.
- 기대 결과:
  - 운영 준비용 직원 기준 화면이라는 점이 분명하게 보인다.
  - 직원 목록이 저장되고 다시 열어도 유지된다.
  - 화면에는 `저장`과 `저장 후 근무표 생성 시작`이 보이며, 예전의 `미리 검사/적용` 흐름처럼 보이지 않는다.
- 관련 자동화 테스트:
  - `tests/unit/step3-employee-info.spec.ts`
  - `tests/e2e/pilot-checklist.spec.ts`

### TC-UI-07: Off 사용 기준을 저장하고 다시 열어도 유지된다

- ID: TC-UI-07
- 목적: 직급 구분과 Off 사용 기준을 저장한 뒤 다시 들어가도 같은 값을 볼 수 있는지 확인한다.
- 사전 조건: `Off 사용 기준 설정` 화면에 접근 가능하다.
- 테스트 단계:
  1. 기본 월간 기준과 연간 기준을 입력한다.
  2. 필요하면 직급 구분을 추가한다.
  3. 필요하면 특정 직급에만 적용되는 기준을 추가한다.
  4. `기준 저장`을 누른다.
  5. 성공 메시지를 확인한다.
  6. 페이지를 새로고침하거나 다른 화면으로 이동했다가 다시 돌아온다.
- 기대 결과:
  - 저장 성공 메시지가 표시된다.
  - 다시 열었을 때 저장한 직급 구분과 기준 값이 그대로 보인다.
  - 현장 관리자는 이 화면만으로 현재 Off 사용 기준을 이해할 수 있다.
- 관련 자동화 테스트:
  - `tests/unit/off-request-policy-table.spec.ts`
  - `tests/unit/phase2-ops-api.spec.ts`

### TC-UI-08: 운영 준비를 마친 뒤 대시보드 상태를 다시 본다

- ID: TC-UI-08
- 목적: 준비 화면들을 저장한 뒤 대시보드가 완료 상태와 다음 작업을 자연스럽게 안내하는지 확인한다.

### TC-UI-11: 월별 생성 Step3에서 직원 정보를 저장하고 Step4로 이동한다

- ID: TC-UI-11
- 목적: 월별 생성 Step3가 현재 구현 기준으로 `저장` 후 Step4로 이어지는지 확인한다.
- 사전 조건: Step2를 통과해 Step3에 접근 가능하고 직원 예시 데이터나 업로드 파일이 있다.
- 테스트 단계:
  1. Step3 제목이 `근무표 생성 - 직원 정보 입력`인지 확인한다.
  2. `직접 입력` 또는 `엑셀 업로드`로 직원을 입력한다.
  3. 직원 목록이 화면에 보이는지 확인한다.
  4. `저장`을 누른다.
  5. 저장 확인 대화상자를 읽고 저장을 진행한다.
  6. 성공 메시지를 확인한다.
  7. `다음 단계 →`를 눌러 이동한다.
- 기대 결과:
  - 저장 확인 대화상자가 보인다.
  - 저장 후 Step3 값이 유지된다.
  - `다음 단계 →`를 누르면 Step4 초기 데이터 입력 화면으로 이동한다.
  - 이 단계는 예전 문서처럼 `미리 검사`와 `적용`으로 나뉘어 보이지 않는다.

## 4. 수동 UI edge case

### TC-UI-E01: 기본 설정이 끝나지 않았을 때 대시보드가 먼저 할 일을 안내한다

- ID: TC-UI-E01
- 위험 시나리오: 현장 관리자가 아직 준비되지 않았는데도 바로 운영을 시작하려고 한다.
- 테스트 단계:
  1. 기본 설정이 완전히 끝나지 않은 계정으로 로그인한다.
  2. 대시보드 상단 카드와 체크리스트를 확인한다.
  3. `기본 설정 열기` 버튼을 누른다.
- 기대 결과:
  - 대시보드가 아직 완료되지 않았다는 문구를 표시한다.
  - 사용자는 기본 설정 화면으로 바로 이동할 수 있다.
- 관련 자동화 테스트:
  - `tests/unit/dashboard.spec.ts`

### TC-UI-E02: 잘못된 파일 업로드는 Step3에서 즉시 막힌다

- ID: TC-UI-E02
- 위험 시나리오: 현장 관리자가 엑셀 형식이 아닌 파일이나 손상된 파일을 업로드한다.
- 테스트 단계:
  1. Step3의 `엑셀 업로드` 탭을 연다.
  2. 지원하지 않는 파일을 업로드한다.
- 기대 결과:
  - 업로드 단계에서 즉시 오류 메시지가 보인다.
  - 잘못된 파일은 직원 목록으로 반영되지 않는다.
- 관련 자동화 테스트:
  - `tests/unit/excel.spec.ts`

### TC-UI-E03: 직원이 없는 상태에서는 다음 단계로 진행할 수 없다

- ID: TC-UI-E03
- 위험 시나리오: 직원 정보를 입력하지 않고 Step3를 통과하려고 한다.
- 테스트 단계:
  1. Step3 화면에서 직원을 한 명도 등록하지 않는다.
  2. `저장` 또는 `다음 단계 →`를 시도한다.
- 기대 결과:
  - 최소 1명 이상의 직원을 등록하라는 안내가 표시된다.
  - Step4로 바로 진행되지 않는다.
- 관련 자동화 테스트:
  - `tests/unit/step3-employee-info.spec.ts`

### TC-UI-E04: Step4에서 초기화 실패가 나면 다시 시도할 수 있다

## 5. 내부 자동 검증 실행 가이드

수동 QA 문서에서 제외한 내부 운영/API 검증은 아래 스크립트로 처리한다.

```bash
./scripts/ops/run-phase2a-go-live-ops-checks.sh
```

### 5.1 스크립트가 기본으로 검증하는 것

- `bootstrap-admin` 계약, 권한, repository 동작
- 일반 운영 auth 경계와 operator auth 경계
- CORS preflight 단위 검증
- 조직/사이트/정책/checklist repository 회귀
- Step2, Step3, Step4, Step5와 fairness summary 관련 단위 회귀

### 5.2 테스트 계정이 있으면 추가로 검증하는 것

- 대시보드 체크리스트 deep link
- 월별 생성 workflow
- Step5 review hub
- 최종 확정 read-only 화면

### 5.3 live bootstrap 환경 변수가 있으면 추가로 검증하는 것

- 실제 `bootstrap-admin` smoke 실행
- operator 토큰과 실제 대상 조직 기준 bootstrap 응답 확인

## 6. 추천 실행 순서

1. 내부 세션에서 `./scripts/ops/run-phase2a-go-live-ops-checks.sh`를 먼저 실행한다.
2. 제3자 수동 QA는 이 문서의 UI 케이스만 브라우저에서 수행한다.
3. 이슈가 나오면 UI 이슈와 내부 운영/API 이슈를 분리해서 기록한다.
