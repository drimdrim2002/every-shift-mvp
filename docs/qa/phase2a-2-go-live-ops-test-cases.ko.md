# Phase2A-2 Go-Live Ops UI 테스트 케이스

이 문서는 제3자 수동 QA 담당자가 브라우저 UI에서 직접 수행할 수 있는 테스트만 정리한 문서다. `bootstrap-admin`, 권한 분리, CORS, DB 반영, RPC 원자성, Auth metadata 정합성, 공정성 ledger write 같은 내부 운영/API 검증은 이 문서 범위에서 제외하고 세션용 쉘 스크립트 `scripts/ops/run-phase2a-go-live-ops-checks.sh`로 자동 실행한다.

## 1. 개요

### 1.1 문서 목적

- 제3자 테스트 담당자가 브라우저 UI만으로 수행할 수 있는 검증 범위를 명확히 한다.
- 운영 파일럿 시작 전에 현장 관리자가 실제로 보게 되는 화면과 동작을 확인한다.
- 내부 구현 이름이나 API 경로를 몰라도 테스트를 진행할 수 있게 한다.

### 1.2 이 문서에서 자주 쓰는 용어

| 용어                     | 쉬운 설명                                                                         |
| ------------------------ | --------------------------------------------------------------------------------- |
| 현장 관리자(pilot admin) | 실제 조직에서 운영 파일럿을 진행하는 관리자 사용자                                |
| 조직/사이트 기본 설정    | 대시보드와 Step2에서 공통으로 사용하는 조직명, 조직 유형, 스케줄 대상 사이트 설정 |
| 스케줄 대상 사이트       | 현재 파일럿 운영에서 기준으로 삼는 대표 사이트                                    |
| 미리 검사                | 실제 반영 전에 입력 내용을 먼저 점검하는 저장 단계                                |
| 실제 적용                | 미리 검사 결과가 나온 뒤 실제 운영 데이터에 반영하는 단계                         |
| 파일럿 준비 체크리스트   | 운영 시작 전에 준비 상태와 바로가기 링크를 보여주는 대시보드 카드                 |
| 정책상 거부된 Off 요청   | Off 요청 정책에 맞지 않아 사유와 함께 거부된 요청                                 |
| 공정성 요약              | 확정 이력을 읽기 전용으로 보여주는 Step5 요약 카드                                |

### 1.3 이번 문서에서 검증하는 범위

- O1: 대시보드의 파일럿 준비 카드와 체크리스트 노출
- O2: 조직/사이트 기본 설정 화면의 저장과 재조회
- O3: Step2의 스케줄 대상 사이트 안내와 인력 기준 입력 UX
- O4: Step3의 직원 입력, 미리 검사, 실제 적용 분리 UX
- O5: Off 요청 정책 설정 화면의 저장과 재진입 UX
- O6: Step5 결과 검토 화면의 탭 전환, 정책 거절 요약, 읽기 전용 상태

### 1.4 이번 문서에서 다루지 않는 범위

- 내부 운영자용 `bootstrap-admin` 실행
- `profiles`, `onboarding_progress`, Auth metadata 직접 확인
- CORS preflight, 허용 메서드, 직접 API 호출
- RPC 호출 여부, 원자적 교체, DB row 직접 조회
- `fairness_ledger_monthly` write 여부와 finalize 내부 구현 확인
- 조직 범위 차단, operator 권한, bootstrap 권한 분리 같은 내부 권한 검증

### 1.5 수동 QA와 내부 자동 검증의 경계

- 제3자 수동 QA는 브라우저 UI만 사용한다.
- 제3자 수동 QA는 SQL Editor, DevTools network payload 확인, curl, Edge Function 직접 호출을 하지 않는다.
- 내부 운영/API 검증은 아래 스크립트로 실행한다.

```bash
./scripts/ops/run-phase2a-go-live-ops-checks.sh
```

## 2. 사전 조건

### 2.1 계정과 데이터 준비

- 현장 관리자 계정은 내부 자동화로 미리 준비되어 있어야 한다.
- 테스트 담당자는 브라우저 로그인만 가능하면 된다.
- 대상 조직에는 아래 데이터가 준비되어 있어야 한다.
  - 조직 row 1개
  - 스케줄 대상 사이트 후보 1개 이상
  - `shifts`와 Step2 표시용 기준 인력 데이터
  - Step3 테스트용 직원 예시 데이터 또는 업로드 가능한 엑셀 파일
  - Off 요청 정책 확인용 기본 정책/직급 정책 예시
  - Step5 검토용 스케줄 1개 이상
  - 최종 확정된 읽기 전용 월 1개 이상

### 2.2 브라우저 기반 수동 QA 환경

- 앱이 실행 중이어야 한다.
- 테스트 담당자는 로그인 가능한 계정을 받아야 한다.
- 제3자 테스트 담당자는 브라우저 UI 외 도구를 사용하지 않는다.

### 2.3 테스트에 필요한 화면

- 대시보드(`/`)
- 조직/사이트 기본 설정(`/ops/organization-setup`)
- Off 요청 정책 설정(`/ops/off-request-policy-setup`)
- Step2 요일별 인력 설정(`/schedule/step2`)
- Step3 직원 정보 입력(`/schedule/step3`)
- Step5 결과 확인(`/schedule/step5/:scheduleId`)

### 2.4 내부 자동 검증 실행용 환경

다음 항목은 제3자 수동 QA가 아니라 세션 자동 검증에서만 사용한다.

- 기본 실행:
  - `pnpm install`
- 브라우저 smoke까지 함께 돌릴 때:
  - `.env.test`
  - `TEST_USER_EMAIL`
  - `TEST_USER_PASSWORD`
- live bootstrap smoke까지 함께 돌릴 때:
  - `SUPABASE_URL`
  - `PHASE2_OPS_OPERATOR_ACCESS_TOKEN`
  - `PHASE2_OPS_BOOTSTRAP_ORGANIZATION_ID`
  - `PHASE2_OPS_BOOTSTRAP_TARGET_EMAIL`
  - `PHASE2_OPS_BOOTSTRAP_DISPLAY_NAME`

## 3. 정상 흐름 UI 테스트 케이스

### TC-UI-01: 대시보드에서 파일럿 준비 상태를 본다

- ID: TC-UI-01
- 목적: 현장 관리자가 로그인 후 대시보드에서 기본 설정 카드와 파일럿 준비 체크리스트를 볼 수 있는지 확인한다.
- 사전 조건: 로그인 가능한 현장 관리자 계정이 있다.
- 테스트 단계:
  1. 로그인 후 대시보드로 이동한다.
  2. `근무표 관리` 화면이 보이는지 확인한다.
  3. `조직/사이트 기본 설정이 완료되었습니다` 또는 `아직 완료되지 않았습니다` 카드가 보이는지 확인한다.
  4. `파일럿 준비 체크리스트` 카드가 보이는지 확인한다.
- 기대 결과:
  - 대시보드에 운영 준비 상태를 설명하는 카드가 표시된다.
  - 체크리스트 카드가 보이고, 준비 단계별 제목이 노출된다.
  - 내부 운영자용 bootstrap 버튼이나 링크는 브라우저 UI에 노출되지 않는다.
- 관련 자동화 테스트:
  - `tests/unit/dashboard.spec.ts`
  - `tests/e2e/pilot-checklist.spec.ts`

### TC-UI-02: 체크리스트 링크로 각 설정 화면에 이동한다

- ID: TC-UI-02
- 목적: 대시보드 체크리스트에서 각 단계로 바로 이동할 수 있는지 확인한다.
- 사전 조건: 체크리스트 카드가 보인다.
- 테스트 단계:
  1. `조직 기본 정보 확인` 링크를 누른다.
  2. `사이트/근무 기본 설정` 링크를 누른다.
  3. `직원 로스터 준비` 링크를 누른다.
  4. `Off 요청 정책 설정` 링크를 누른다.
  5. `최종 검토 진입` 링크를 누른다.
- 기대 결과:
  - 각 링크가 해당 화면으로 이동한다.
  - 이동 후 화면 제목이 현재 단계와 일치한다.
  - 사용자는 대시보드에서 바로 다음 작업으로 진입할 수 있다.
- 관련 자동화 테스트:
  - `tests/e2e/pilot-checklist.spec.ts`

### TC-UI-03: 조직 기본 정보를 저장하고 새로고침 후 다시 본다

- ID: TC-UI-03
- 목적: 조직명과 조직 유형을 UI에서 저장하고 다시 열었을 때 값이 유지되는지 확인한다.
- 사전 조건: `조직/사이트 기본 설정` 화면에 접근 가능하다.
- 테스트 단계:
  1. `조직 기본 정보` 카드에서 조직명을 입력한다.
  2. 조직 유형을 입력한다.
  3. `조직 정보 저장` 버튼을 누른다.
  4. 성공 메시지를 확인한다.
  5. 페이지를 새로고침한다.
- 기대 결과:
  - 저장 성공 메시지가 표시된다.
  - 새로고침 후에도 저장한 조직명과 조직 유형이 그대로 보인다.
  - 대시보드 기본 설정 상태가 갱신된다.
- 관련 자동화 테스트:
  - `tests/unit/phase2-ops-api.spec.ts`
  - `tests/unit/dashboard.spec.ts`

### TC-UI-04: 스케줄 대상 사이트를 한 곳만 지정한다

- ID: TC-UI-04
- 목적: 사이트를 여러 개 입력하더라도 UI에서는 스케줄 대상 사이트가 한 곳만 선택되도록 동작하는지 확인한다.
- 사전 조건: `조직/사이트 기본 설정` 화면에 접근 가능하다.
- 테스트 단계:
  1. 사이트를 2개 이상 입력한다.
  2. 첫 번째 사이트를 `스케줄 대상 사이트`로 선택한다.
  3. 두 번째 사이트를 다시 `스케줄 대상 사이트`로 선택한다.
  4. `사이트 설정 저장` 버튼을 누른다.
  5. 페이지를 새로고침한다.
- 기대 결과:
  - 마지막으로 선택한 사이트만 스케줄 대상 사이트로 체크된다.
  - 동시에 두 개가 선택된 상태로 남지 않는다.
  - 새로고침 후에도 한 개의 대표 사이트만 보인다.
- 관련 자동화 테스트:
  - `tests/unit/phase2-ops-api.spec.ts`

### TC-UI-05: Step2에서 현재 스케줄 대상 사이트 안내와 인력 기준을 확인한다

- ID: TC-UI-05
- 목적: Step2가 현재 스케줄 대상 사이트 문구를 보여주고, 요일별 필요 인력을 수정할 수 있는지 확인한다.
- 사전 조건: 스케줄 대상 사이트가 저장되어 있고 Step2에 접근 가능하다.
- 테스트 단계:
  1. Step2를 연다.
  2. 상단 카드 제목이 `근무표 생성 - 요일별 인력 설정`인지 확인한다.
  3. `현재 스케줄 대상 사이트` 안내 문구가 보이는지 확인한다.
  4. 월요일 또는 화요일의 필요 인력 수를 수정한다.
  5. `다음 단계 →`로 이동한 뒤 다시 Step2로 돌아온다.
- 기대 결과:
  - 현재 대표 사이트 안내 문구가 표시된다.
  - 입력한 인력 수가 다시 열었을 때 유지된다.
  - 사용자는 사이트 메타데이터와 인력 기준을 같은 운영 흐름에서 이해할 수 있다.
- 관련 자동화 테스트:
  - `tests/unit/step2-site-info.spec.ts`
  - `tests/e2e/schedule-workflow.spec.ts`

### TC-UI-06: Step3에서 미리 검사 후 실제 적용으로 진행한다

- ID: TC-UI-06
- 목적: Step3의 직원 입력 흐름이 `저장`과 `적용`으로 나뉘어 보이는지 확인한다.
- 사전 조건: Step3에 접근 가능하고 업로드 파일 또는 수동 입력용 데이터가 있다.
- 테스트 단계:
  1. 직원을 직접 입력하거나 엑셀 파일을 업로드한다.
  2. 직원 목록이 화면에 보이는지 확인한다.
  3. 저장 전에는 `적용 →` 버튼이 비활성인지 확인한다.
  4. `저장` 버튼을 누른다.
  5. 검증 결과 안내가 보이는지 확인한다.
  6. `적용 →` 버튼을 누른다.
- 기대 결과:
  - 저장 전에는 적용할 수 없다.
  - 저장 후 검증 결과가 표시되고 적용 가능 상태가 된다.
  - 적용 후 결과 확인 단계로 이동한다.
- 관련 자동화 테스트:
  - `tests/unit/step3-employee-info.spec.ts`
  - `tests/e2e/schedule-workflow.spec.ts`

### TC-UI-07: Step3에서 다시 수정하면 적용 준비 상태가 초기화된다

- ID: TC-UI-07
- 목적: Step3에서 한 번 저장한 뒤 데이터를 다시 수정하면, 사용자가 다시 미리 검사를 해야 한다는 점이 UI에서 드러나는지 확인한다.
- 사전 조건: Step3에서 한 번 저장해 검증 결과가 보이는 상태다.
- 테스트 단계:
  1. 직원 이름, 가능 시프트, 또는 직원 한 명을 수정한다.
  2. 검증 결과 안내 상태를 확인한다.
  3. `적용 →` 버튼 상태를 확인한다.
  4. 다시 `저장` 버튼을 눌러 검증을 재실행한다.
- 기대 결과:
  - 데이터를 수정하면 이전 검증 결과에 그대로 의존하지 않는다.
  - `적용 →` 버튼은 다시 비활성화되거나 즉시 진행되지 않는다.
  - 재저장 후에만 다시 적용 가능 상태가 된다.
- 관련 자동화 테스트:
  - `tests/unit/step3-employee-info.spec.ts`

### TC-UI-08: 잘못된 파일이나 잘못된 직원 데이터는 UI에서 바로 경고한다

- ID: TC-UI-08
- 목적: 제3자 테스트 담당자가 잘못된 파일 형식이나 오류가 있는 직원 데이터를 넣었을 때 UI가 즉시 안내하는지 확인한다.
- 사전 조건: 잘못된 파일 또는 중복/누락 데이터가 준비되어 있다.
- 테스트 단계:
  1. `.xlsx`, `.xls`가 아닌 파일을 업로드해 본다.
  2. 중복 직원 ID 또는 존재하지 않는 시프트 코드가 포함된 파일을 업로드한다.
  3. `저장`을 눌러 검증 결과를 확인한다.
- 기대 결과:
  - 잘못된 파일 형식은 업로드 단계에서 오류 메시지가 나온다.
  - 잘못된 직원 데이터는 검증 결과 영역에서 경고로 표시된다.
  - 오류가 해결되기 전에는 적용으로 진행되지 않는다.
- 관련 자동화 테스트:
  - `tests/unit/step3-employee-info.spec.ts`
  - `tests/unit/excel.spec.ts`

### TC-UI-09: Off 요청 정책을 저장하고 다시 열어도 값이 유지된다

- ID: TC-UI-09
- 목적: 조직 기본 정책과 rank별 정책을 저장한 뒤 다시 들어가도 화면에서 같은 값을 볼 수 있는지 확인한다.
- 사전 조건: `Off 요청 정책 설정` 화면에 접근 가능하다.
- 테스트 단계:
  1. 기본 월간 정책과 기본 연간 정책을 입력한다.
  2. 필요하면 rank 코드를 추가하고 rank별 정책도 입력한다.
  3. `정책 저장` 버튼을 누른다.
  4. 성공 메시지를 확인한다.
  5. 페이지를 새로고침하거나 다른 화면으로 이동한 뒤 다시 돌아온다.
- 기대 결과:
  - 저장 성공 메시지가 표시된다.
  - 다시 열었을 때 저장한 정책 값이 그대로 보인다.
  - 현장 관리자는 정책 설정 화면만으로 현재 운영 정책을 확인할 수 있다.
- 관련 자동화 테스트:
  - `tests/unit/off-request-policy-table.spec.ts`
  - `tests/unit/phase2-ops-api.spec.ts`

### TC-UI-10: 대시보드 체크리스트와 준비 상태가 실제 화면 흐름과 이어진다

- ID: TC-UI-10
- 목적: 조직 설정, Step2, Step3, 정책 설정을 진행한 뒤 대시보드가 다음 작업을 자연스럽게 안내하는지 확인한다.
- 사전 조건: 기본 설정과 일부 준비 단계가 완료되어 있다.
- 테스트 단계:
  1. 대시보드로 돌아간다.
  2. 기본 설정 카드 문구를 확인한다.
  3. 체크리스트 각 항목의 상태 문구를 확인한다.
  4. 아직 남은 항목이 있으면 해당 링크를 눌러 이동한다.
- 기대 결과:
  - 대시보드는 완료된 항목과 남은 항목을 구분해서 보여준다.
  - 사용자는 다음 작업을 체크리스트 링크로 바로 수행할 수 있다.
  - 준비 여부는 화면 흐름 기준으로 이해 가능해야 한다.
- 관련 자동화 테스트:
  - `tests/unit/dashboard.spec.ts`
  - `tests/unit/phase2-ops-checklist.spec.ts`
  - `tests/e2e/pilot-checklist.spec.ts`

### TC-UI-11: Step5에서 검토 탭을 오가며 결과를 읽을 수 있다

- ID: TC-UI-11
- 목적: Step5가 grid, proof, off-request 탭을 같은 검토 화면 안에서 제공하는지 확인한다.
- 사전 조건: 검토 가능한 스케줄이 있고 Step5에 접근 가능하다.
- 테스트 단계:
  1. 대시보드에서 기존 스케줄 하나를 연다.
  2. Step5에서 grid 탭이 보이는지 확인한다.
  3. proof 탭으로 이동한다.
  4. off-request 탭으로 이동한다.
  5. 다시 grid 탭으로 돌아온다.
- 기대 결과:
  - 세 탭이 같은 검토 화면 안에서 전환된다.
  - 탭 전환만으로 다른 페이지로 튀지 않는다.
  - 결과 검토 흐름이 한 화면 안에서 이어진다.
- 관련 자동화 테스트:
  - `tests/e2e/step5-review-hub.spec.ts`

### TC-UI-12: Step5에서 정책상 거부된 Off 요청과 읽기 전용 공정성 요약을 본다

- ID: TC-UI-12
- 목적: 결과 확인 화면에서 정책상 거부된 Off 요청 요약과 공정성 요약이 읽기 전용으로 표시되는지 확인한다.
- 사전 조건: 정책상 거부된 Off 요청 또는 공정성 요약 데이터가 있는 스케줄이 있다.
- 테스트 단계:
  1. Step5 결과 확인 화면을 연다.
  2. `정책상 거부된 Off 요청` 경고 영역이 있으면 문구를 읽는다.
  3. `공정성 요약` 카드가 있으면 읽는다.
  4. 요약 카드 안에 직접 수정 버튼이나 입력창이 있는지 확인한다.
- 기대 결과:
  - 거부된 Off 요청은 요약 문구로 설명된다.
  - 공정성 요약은 읽기 전용 정보로 보인다.
  - 사용자가 요약 자체를 편집하는 UI는 노출되지 않는다.
- 관련 자동화 테스트:

  - `tests/unit/phase2-ops-checklist.spec.ts`

## 4. 수동 UI edge case

### TC-UI-E01: 기본 설정이 끝나지 않았을 때 대시보드가 먼저 할 일을 안내한다

- ID: TC-UI-E01
- 위험 시나리오: 현장 관리자가 아직 준비되지 않았는데도 바로 운영을 시작하려고 한다.
- 테스트 단계:
  1. 기본 설정이 완전히 끝나지 않은 계정으로 로그인한다.
  2. 대시보드 상단 카드와 체크리스트를 확인한다.
  3. `기본 설정 열기` 버튼을 누른다.
- 기대 결과:
  - 대시보드가 아직 완료되지 않았다는 문구를 표시한다.
  - 사용자는 기본 설정 화면으로 바로 이동할 수 있다.
- 관련 자동화 테스트:
  - `tests/unit/dashboard.spec.ts`

### TC-UI-E02: 잘못된 파일 업로드는 Step3에서 즉시 막힌다

- ID: TC-UI-E02
- 위험 시나리오: 현장 관리자가 엑셀 형식이 아닌 파일이나 손상된 파일을 업로드한다.
- 테스트 단계:
  1. Step3의 엑셀 업로드 탭을 연다.
  2. 지원하지 않는 파일을 업로드한다.
- 기대 결과:
  - 업로드 단계에서 즉시 오류 메시지가 보인다.
  - 잘못된 파일은 직원 목록으로 반영되지 않는다.
- 관련 자동화 테스트:
  - `tests/unit/excel.spec.ts`

### TC-UI-E03: 검증 경고가 있는 상태에서는 Step3 적용으로 넘어가지 않는다

- ID: TC-UI-E03
- 위험 시나리오: 중복 직원 ID나 누락 시프트가 있는 상태로 실제 적용을 시도한다.
- 테스트 단계:
  1. 오류가 있는 직원 데이터를 준비한다.
  2. Step3에서 `저장`을 눌러 검증 결과를 확인한다.
  3. `적용 →` 버튼 상태를 확인한다.
- 기대 결과:
  - 경고가 보이고 오류 수정 안내가 표시된다.
  - 적용으로 바로 진행되지 않는다.
- 관련 자동화 테스트:
  - `tests/unit/step3-employee-info.spec.ts`

## 5. 내부 자동 검증 실행 가이드

수동 QA 문서에서 제외한 내부 운영/API 검증은 아래 스크립트로 처리한다.

```bash
./scripts/ops/run-phase2a-go-live-ops-checks.sh
```

### 5.1 스크립트가 기본으로 검증하는 것

- `bootstrap-admin` 계약, 권한, repository 동작
- 일반 운영 auth 경계와 operator auth 경계
- CORS preflight 단위 검증
- 조직/사이트/정책/checklist repository 회귀
- Off 정책, Step3 validate/apply, schedule write/read, fairness summary 관련 단위 회귀

### 5.2 테스트 계정이 있으면 추가로 검증하는 것

- 대시보드 체크리스트 deep link
- Step3 흐름
- Step5 review hub
- 최종 확정 read-only 화면

### 5.3 live bootstrap 환경 변수가 있으면 추가로 검증하는 것

- 실제 `bootstrap-admin` smoke 실행
- operator 토큰과 실제 대상 조직 기준 bootstrap 응답 확인

## 6. 추천 실행 순서

1. 내부 세션에서 `./scripts/ops/run-phase2a-go-live-ops-checks.sh`를 먼저 실행한다.
2. 제3자 수동 QA는 이 문서의 UI 케이스만 브라우저에서 수행한다.
3. 이슈가 나오면 UI 이슈와 내부 운영/API 이슈를 분리해서 기록한다.
