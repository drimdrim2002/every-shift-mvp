# Phase2A 통합 UI 테스트 시나리오

작성일: 2026-04-02
대상: 개발자가 아닌 QA, 기획, 운영 검증자
적용 범위: `PHASE2A_EXECUTION_SLICES.md`의 모든 slice 구현 완료 상태

## 1. 이 문서로 무엇을 테스트하나요?

이 문서는 `이미 스케줄링이 끝난 데이터`를 기준으로, 제3자가 대시보드에서 기존 근무표를 열어 `Step5 결과 확인 화면`을 통합 검증하는 가이드입니다.

이번 문서는 아래를 전제로 합니다.

- Step1 기본 정보
- Step2 사이트 정보
- Step3 직원 정보

위 3개는 이미 충분히 검증되었습니다.
따라서 이번 문서는 `대시보드 -> 기존 근무표 열기 -> Step5 review hub 확인` 흐름만 다룹니다.

핵심 확인 항목은 아래 8개입니다.

1. 대시보드에서 기존 근무표를 열면 Step5로 진입되는지
2. Step5 상단에 `버전 비교` 영역이 항상 보이는지
3. `미리보기`와 `선택됨`이 서로 다른 개념으로 동작하는지
4. 상태별 안내 패널이 올바르게 열리는지
5. primary action 버튼이 현재 상태에 맞게 1개만 강조되는지
6. `다시 검토`, `확정`, `다시 생성` 흐름이 상태에 맞게 동작하는지
7. `finalized` 상태에서 수정이 차단되는지
8. finalized 월에서 Step3 직원 재저장이 차단되는지

## 2. 어려운 용어를 먼저 쉽게 설명합니다

- `미리보기 버전`: 지금 화면에서 보고 있는 버전
- `선택된 버전`: 현재 시스템이 기준으로 삼는 버전
- `확정됨`: 더 이상 수정하면 안 되는 최종 버전
- `재검토 필요`: 수동 수정이 생겨서 다시 검토가 필요한 상태
- `검토 차단`: 하드 제약 위반 때문에 바로 확정할 수 없는 상태
- `생성 불가`: 조건상 해를 만들 수 없는 상태
- `생성 실패`: 엔진 실행 자체가 실패한 상태

테스터는 아래 한 줄만 기억하면 충분합니다.

`카드 클릭 = 미리보기만 변경`
`버튼 클릭 = 선택 또는 상태 변경`

## 3. 테스트 전 준비

### 3.1 개발자가 먼저 준비해야 하는 fixture

아래 테스트 월 또는 테스트 카드가 미리 준비되어 있어야 합니다.

| 별칭         | 필요한 상태                   | 주 용도                           | 파괴적 테스트 허용 |
| ------------ | ----------------------------- | --------------------------------- | ------------------ |
| `BASE-MULTI` | 버전 2개 이상, finalized 아님 | preview/selected 분리 확인        | 아니오             |
| `READY`      | `review_ready`                | grid-first, finalize 전 정상 상태 | 예                 |
| `PENDING`    | `review_pending`              | 재검토 필요 상태 확인             | 아니오             |
| `BLOCKED`    | `review_blocked`              | proof-first 상태 확인             | 아니오             |
| `INFEASIBLE` | `infeasible`                  | 생성 불가 패널 확인               | 아니오             |
| `FAILED`     | `solve_failed`                | 실패 패널, retry 확인             | 아니오             |
| `FINALIZED`  | `finalized`                   | 읽기 전용, Step3 보호 확인        | 아니오             |

개발자가 QA에게 꼭 전달해야 하는 정보:

- 어떤 대시보드 카드가 어떤 별칭인지
- 각 카드의 월 이름
- `BASE-MULTI`는 버전이 2개 이상 보인다는 점
- `READY`는 실제로 버튼 테스트를 해도 되는 파괴적 fixture라는 점

### 3.2 테스터가 준비할 것

1. 테스트 계정으로 로그인합니다.
2. 대시보드(`/`)에 접근할 수 있어야 합니다.
3. 가능하면 같은 브라우저 탭에서 끝까지 테스트합니다.
4. 실패가 나면 스크린샷을 남깁니다.

## 4. 공통 진입 방법

모든 시나리오는 아래 방식으로 시작합니다.

1. 로그인합니다.
2. 대시보드에서 개발자가 지정한 테스트 월 카드를 찾습니다.
3. `수정` 버튼이 아니라 카드 본문을 클릭합니다.
4. Step5로 이동했는지 확인합니다.
5. 화면 상단에 아래 3개가 보이는지 먼저 확인합니다.
   - `버전 비교`
   - `미리보기 버전`
   - `선택된 버전`

Step5 진입 성공 기준:

- 카드 제목이 `근무표 생성 - 결과 확인`
- 주소가 `/schedule/step5/<scheduleId>?version=<something>` 형태
- 상단에 `버전 비교` 영역이 보임

## 5. 실행 시나리오

### 시나리오 A. 대시보드에서 기존 근무표 열기

대상 fixture: 아무 fixture나 가능

목적: 기존 완료 근무표가 Step5로 정상 진입되는지 확인

실행:

1. 대시보드에서 테스트 카드를 찾습니다.
2. 카드 본문을 클릭합니다.

기대 결과:

- Step5로 이동합니다.
- 주소에 `?version=`이 붙어 있습니다.
- 상단 compare 영역이 보입니다.

실패로 기록할 예:

- 카드 클릭 시 Step1이나 Step4로 이동함
- Step5는 열렸지만 `버전 비교`가 없음

### 시나리오 B. compare surface는 항상 보이는지 확인

대상 fixture: 아무 fixture나 가능

목적: 상태가 달라도 Step5의 공통 프레임이 유지되는지 확인

실행:

1. Step5에 들어간 뒤 화면 상단을 확인합니다.
2. 스크롤을 조금 내려도 compare 영역이 화면 상단에 남아 있는지 확인합니다.
3. review tab을 바꿔도 compare 영역이 유지되는지 확인합니다.

기대 결과:

- `버전 비교` 영역이 사라지지 않습니다.
- 하단 grid나 패널 상태와 관계없이 같은 프레임이 유지됩니다.

### 시나리오 C. 카드 클릭은 미리보기만 바꾸는지 확인

대상 fixture: `BASE-MULTI`

목적: preview와 selected가 분리되어 동작하는지 확인

실행:

1. `선택됨`이 붙어 있지 않은 다른 버전 카드를 찾습니다.
2. 해당 카드를 클릭합니다.
3. `미리보기` 칩이 이동했는지 확인합니다.
4. `선택됨` 칩은 그대로인지 확인합니다.
5. 오른쪽 요약 영역의 `미리보기 버전`과 `선택된 버전`도 함께 확인합니다.

기대 결과:

- 클릭한 카드로 `미리보기`만 이동합니다.
- `선택됨`은 원래 카드에 그대로 남아 있습니다.
- compare 영역은 사라지지 않습니다.

실패로 기록할 예:

- 카드 클릭만으로 `선택됨`도 같이 바뀜
- 카드 클릭 후 화면이 깨짐

### 시나리오 D. explicit select 버튼으로만 선택 버전이 바뀌는지 확인

대상 fixture: `BASE-MULTI`

목적: authoritative selection이 버튼으로만 바뀌는지 확인

실행:

1. 시나리오 C를 수행해 `미리보기`와 `선택됨`이 다른 상태를 만듭니다.
2. action area에서 버튼 라벨을 확인합니다.
3. `이 버전을 선택` 버튼을 클릭합니다.

기대 결과:

- 버튼을 누른 뒤에만 `선택됨`이 현재 `미리보기` 카드로 이동합니다.
- 주소의 `version` 값은 현재 미리보기 값을 유지합니다.

실패로 기록할 예:

- 버튼 없이 selection이 바뀜
- 버튼 클릭 후에도 selection이 그대로임

### 시나리오 E. 상태별 기본 패널이 올바른지 확인

대상 fixture: `READY`, `PENDING`, `BLOCKED`, `INFEASIBLE`, `FAILED`, `FINALIZED`

목적: 각 상태에서 첫 화면의 안내 패널이 맞는지 확인

아래 표대로 확인합니다.

| fixture      | 첫 화면에서 먼저 보여야 하는 것 |
| ------------ | ------------------------------- |
| `READY`      | grid 중심 화면                  |
| `PENDING`    | `재검토 필요` 패널              |
| `BLOCKED`    | `하드 제약 위반 요약` 패널      |
| `INFEASIBLE` | `생성 불가` 패널                |
| `FAILED`     | `생성 실패` 패널                |
| `FINALIZED`  | grid 중심 + 읽기 전용 상태      |

실행:

1. 각 fixture를 하나씩 엽니다.
2. Step5 detail area의 첫 패널 제목을 확인합니다.
3. compare 영역이 계속 보이는지도 함께 확인합니다.

기대 결과:

- 각 상태에 맞는 패널이 먼저 열립니다.
- 패널이 바뀌어도 compare 영역은 유지됩니다.

### 시나리오 F. review tab 전환이 공통 shell 안에서 동작하는지 확인

대상 fixture: `READY` 또는 `BLOCKED`

목적: grid, proof, off-request 탭이 공통 프레임 안에서 전환되는지 확인

실행:

1. `배정표` 탭을 확인합니다.
2. `하드 제약` 탭을 클릭합니다.
3. `Off 요청` 탭을 클릭합니다.
4. 다시 `배정표` 탭으로 돌아옵니다.

기대 결과:

- 탭 클릭 시 해당 내용만 바뀝니다.
- 상단 compare 영역과 action area는 유지됩니다.

실패로 기록할 예:

- 탭을 바꾸면 페이지 전체가 깨짐
- 일부 탭이 열리지 않음

### 시나리오 G. `review_pending -> 다시 검토 -> review_ready` 흐름 확인

대상 fixture: `PENDING`

목적: 재검토 버튼이 실제 상태 전환을 유도하는지 확인

실행:

1. `재검토 필요` 안내가 보이는지 확인합니다.
2. primary action 버튼이 `다시 검토`인지 확인합니다.
3. `다시 검토` 버튼을 클릭합니다.
4. 처리 완료 후 화면을 다시 확인합니다.

기대 결과:

- pending 안내가 사라지거나 약해집니다.
- 상태가 `review_ready` 또는 현재 데이터에 맞는 다음 정상 상태로 바뀝니다.
- primary action이 `이 버전 확정` 또는 그 상태에 맞는 단일 버튼으로 바뀝니다.

실패로 기록할 예:

- 버튼 클릭 후 상태 변화가 없음
- 여전히 `재검토 필요`로 고정됨

### 시나리오 H. `review_ready -> 확정` 흐름 확인

대상 fixture: `READY`

목적: 확정 버튼과 finalized 잠금 동작을 확인

실행:

1. `READY` fixture를 엽니다.
2. primary action 버튼이 `이 버전 확정`인지 확인합니다.
3. 버튼을 클릭합니다.
4. 완료 후 새로고침합니다.

기대 결과:

- 현재 버전에 `확정됨` 표시가 보입니다.
- 읽기 전용 안내가 보입니다.
- grid가 편집되지 않습니다.

실패로 기록할 예:

- 확정 후에도 수정 가능
- `확정됨` 표시가 없음

### 시나리오 I. `solve_failed`에서는 retry가 primary인지 확인

대상 fixture: `FAILED`

목적: 실패 상태에서 올바른 recovery CTA가 노출되는지 확인

실행:

1. `FAILED` fixture를 엽니다.
2. `생성 실패` 패널이 먼저 보이는지 확인합니다.
3. `Trace ID`가 보이는지 확인합니다.
4. primary action 버튼 라벨을 확인합니다.

기대 결과:

- `생성 실패` 패널이 먼저 보입니다.
- 실패 이유 또는 요약이 보입니다.
- 가능하면 `Trace ID`가 보입니다.
- primary action은 `다시 생성` 1개만 강하게 보입니다.

### 시나리오 J. finalized 상태에서는 편집이 막히는지 확인

대상 fixture: `FINALIZED`

목적: 읽기 전용 보호가 실제로 동작하는지 확인

실행:

1. `FINALIZED` fixture를 엽니다.
2. 임의 셀을 수정하려고 시도합니다.
3. `저장`, `더 개선하기` 버튼 상태를 확인합니다.

기대 결과:

- 셀 수정이 되지 않습니다.
- 저장과 편집 계열 동작이 막혀 있습니다.
- 읽기 전용 안내가 보입니다.

실패로 기록할 예:

- 확정 상태인데 편집 가능
- 저장 버튼이 활성화됨

### 시나리오 K. 엑셀 다운로드가 가능한지 확인

대상 fixture: `READY` 또는 `FINALIZED`

목적: 결과 화면에서 export 진입이 가능한지 확인

실행:

1. Step5 하단에서 `엑셀 다운로드` 버튼을 찾습니다.
2. 버튼을 클릭합니다.

기대 결과:

- 브라우저 다운로드가 시작되거나 저장 동작이 트리거됩니다.
- 화면 오류가 발생하지 않습니다.

참고:

- 파일 내용 자체의 정합성은 이 문서 범위 밖입니다.
- 이번 문서에서는 버튼이 정상 동작하는지만 확인합니다.

### 시나리오 L. finalized 월은 Step3에서 직원 재저장이 차단되는지 확인

대상 fixture: `FINALIZED`

목적: finalized된 월을 다시 열어 Step3에서 저장하려고 할 때 보호가 동작하는지 확인

실행:

1. 대시보드로 돌아갑니다.
2. `FINALIZED` 카드의 `수정` 버튼을 클릭합니다.
3. Step1에서 `다음 단계`를 클릭합니다.
4. Step2에서 `다음 단계`를 클릭합니다.
5. Step3에서 `저장` 버튼을 클릭합니다.

기대 결과:

- 아래 에러 메시지가 보입니다.
  `현재 월에 확정된 근무표가 있어 직원 정보를 다시 저장할 수 없습니다.`
- 직원 재생성 흐름이 진행되지 않습니다.
- 파괴적 확인창이 뜨지 않습니다.

실패로 기록할 예:

- finalized 월인데 Step3 저장이 진행됨
- 직원/스케줄 삭제 경고창이 뜸
