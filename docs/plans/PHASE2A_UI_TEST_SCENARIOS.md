# Phase2A 통합 UI 테스트 시나리오

작성일: 2026-04-03  
대상: 개발자가 아닌 QA, 기획, 운영 검증자  
적용 범위: Step5 결과 확인 화면의 `비교 중심 UX`

## 1. 이 문서는 무엇을 확인하나요?

이 문서는 이미 생성이 끝난 근무표를 Step5에서 열었을 때, 사용자가 여러 안을 `비교`, `자세히 보기`, `기준안 선택`, `최종 확정` 순서로 자연스럽게 사용할 수 있는지 확인하는 가이드입니다.

이번 문서의 핵심 확인 항목은 아래 9개입니다.

1. finalized가 아닌 월에서는 `비교 도구`를 통해 `비교 후보`와 `비교 워크스페이스`를 볼 수 있는지
2. 카드 클릭 규칙을 몰라도 `비교에 추가`, `이 안 자세히 보기`, `이 안을 기준안으로 사용`으로 흐름을 이해할 수 있는지
3. 두 안을 비교했을 때 핵심 차이가 문장으로 먼저 보이는지
4. `현재 자세히 보는 안`과 `현재 기준안`이 분리되어 보이는지
5. `다시 검사`, `최종 확정`, `다시 생성`이 상태에 맞게 하나만 강조되는지
6. `규칙 위반`, `생성 불가`, `생성 실패`가 서로 다른 안내 패널로 보이는지
7. 사용자가 `비교 도구`를 숨기고 다시 펼칠 수 있는지
8. `최종 확정됨` 상태에서는 비교 도구가 아예 보이지 않고 편집도 막히는지
9. finalized 월에서 Step3 직원 재저장이 차단되는지

## 2. 어려운 용어를 먼저 쉽게 설명합니다

- `비교 후보`: 지금 비교할 수 있는 버전 목록
- `비교 워크스페이스`: 현재 비교 중인 안 1~2개를 보여주는 영역
- `비교 도구`: `비교 후보`와 `비교 워크스페이스`를 묶어 보여주는 상단 영역
- `현재 자세히 보는 안`: 하단 grid/proof/off 요청 탭이 기준으로 삼는 안
- `현재 기준안`: 시스템이 현재 공식 후보로 잡고 있는 안
- `최종 확정됨`: 더 이상 수정하면 안 되는 최종 버전
- `수정 후 다시 검사 필요`: 사람이 손으로 수정해서 다시 검토가 필요한 상태
- `규칙 위반으로 확정 불가`: 하드 제약 위반 때문에 확정할 수 없는 상태
- `조건 충돌로 생성 불가`: 조건상 답을 만들 수 없는 상태
- `생성 중 오류 발생`: 엔진 실행 자체가 실패한 상태

테스터는 아래 세 줄만 기억하면 충분합니다.

`비교에 추가 = 비교 워크스페이스에 올림`
`이 안 자세히 보기 = 하단 상세 화면 기준 변경`
`이 안을 기준안으로 사용 = 시스템 공식 후보 변경`

## 3. 테스트 전 준비

### 3.1 개발자가 준비해야 하는 fixture

| 별칭         | 필요한 상태                   | 주 용도                                | 파괴적 테스트 허용 |
| ------------ | ----------------------------- | -------------------------------------- | ------------------ |
| `BASE-MULTI` | 버전 3개 이상, finalized 아님 | 비교 후보/비교 워크스페이스 확인       | 아니오             |
| `READY`      | `review_ready`                | 기준안 선택, grid-first, finalize 확인 | 예                 |
| `PENDING`    | `review_pending`              | 수정 후 다시 검사 필요 상태 확인       | 아니오             |
| `BLOCKED`    | `review_blocked`              | 규칙 위반 패널, proof-first 확인       | 아니오             |
| `INFEASIBLE` | `infeasible`                  | 생성 불가 패널 확인                    | 아니오             |
| `FAILED`     | `solve_failed`                | 실패 패널, retry 확인                  | 아니오             |
| `FINALIZED`  | `finalized`                   | 읽기 전용, Step3 보호 확인             | 아니오             |

개발자가 QA에게 꼭 전달해야 하는 정보:

- 어떤 대시보드 카드가 어떤 fixture인지
- 각 fixture의 월 이름
- `BASE-MULTI`는 버전이 3개 이상이라는 점
- `READY`는 버튼 테스트를 해도 되는 파괴적 fixture라는 점

### 3.2 테스터가 준비할 것

1. 테스트 계정으로 로그인합니다.
2. 대시보드(`/`)에 접근할 수 있어야 합니다.
3. 가능하면 같은 브라우저 탭에서 끝까지 테스트합니다.
4. 실패가 나면 스크린샷을 남깁니다.

## 4. 공통 진입 방법

모든 시나리오는 아래 방식으로 시작합니다.

1. 로그인합니다.
2. 대시보드에서 개발자가 지정한 테스트 월 카드를 찾습니다.
3. 카드 본문을 클릭합니다.
4. Step5로 이동했는지 확인합니다.
5. 화면 상단 구성을 확인합니다.
   - finalized가 아닌 월이면 `비교 도구`
   - finalized가 아닌 월이면 그 안에 `비교 후보`, `비교 워크스페이스`
   - `현재 자세히 보는 안`
   - `현재 기준안`

Step5 진입 성공 기준:

- 카드 제목이 `근무표 생성 - 결과 확인`
- 주소가 `/schedule/step5/<scheduleId>?version=<something>` 형태
- finalized가 아니면 `비교 도구`가 보임
- finalized면 `비교 도구` 없이 바로 읽기 전용 상세 화면이 보임

## 5. 실행 시나리오

### 시나리오 A. finalized가 아닌 기존 근무표를 열면 비교 중심 Step5로 진입되는지 확인

대상 fixture: `BASE-MULTI`, `READY`, `PENDING`, `BLOCKED`, `INFEASIBLE`, `FAILED`

실행:

1. 대시보드에서 테스트 카드를 찾습니다.
2. 카드 본문을 클릭합니다.

기대 결과:

- Step5로 이동합니다.
- `비교 도구`가 먼저 보입니다.
- 펼쳐진 상태에서는 `비교 후보`, `비교 워크스페이스`가 함께 보입니다.
- `현재 자세히 보는 안`, `현재 기준안` 요약이 보입니다.

### 시나리오 B. `비교 도구`를 숨기고 다시 펼칠 수 있는지 확인

대상 fixture: `BASE-MULTI`

실행:

1. 상단의 `비교 도구` 영역을 찾습니다.
2. `숨기기`를 클릭합니다.
3. 비교 도구 영역 안의 내용이 접히는지 확인합니다.
4. `다시 보기`를 클릭합니다.

기대 결과:

- 접으면 `비교 후보`, `비교 워크스페이스`가 사라집니다.
- `현재 자세히 보는 안`과 하단 상세 화면은 그대로 유지됩니다.
- 다시 펼치면 기존 비교 상태가 유지된 채 다시 보입니다.

### 시나리오 C. 비교 후보에서 명시적 액션이 보이는지 확인

대상 fixture: `BASE-MULTI`

실행:

1. 버전 카드들을 확인합니다.
2. 각 카드에 아래 버튼이 보이는지 확인합니다.
   - `비교에 추가`
   - `이 안 자세히 보기`
   - `이 안을 기준안으로 사용`

기대 결과:

- 사용자가 카드 클릭 규칙을 몰라도 행동을 이해할 수 있습니다.
- 현재 기준안 카드에는 `현재 기준안` 배지가 붙습니다.
- 현재 자세히 보는 안에는 `지금 자세히 보는 안` 배지가 붙습니다.
- 현재 자세히 보는 안의 compare 버튼은 `현재 보는 안`처럼 눌릴 수 없는 상태로 보입니다.

### 시나리오 D. `비교에 추가`로 두 안을 워크스페이스에 올릴 수 있는지 확인

대상 fixture: `BASE-MULTI`

실행:

1. 현재 자세히 보는 안이 아닌 다른 안에서 `비교에 추가`를 클릭합니다.
2. 필요하면 또 다른 안도 `비교에 추가`합니다.
3. `비교 워크스페이스`를 확인합니다.

기대 결과:

- 워크스페이스에 좌/우 두 슬롯이 보입니다.
- 비교 중인 안이 2개면 `핵심 차이` 요약이 문장으로 보입니다.
- 카드에는 `비교 중` 배지가 붙습니다.

### 시나리오 E. `이 안 자세히 보기`가 하단 상세 영역 기준만 바꾸는지 확인

대상 fixture: `BASE-MULTI`

실행:

1. 현재 자세히 보는 안이 아닌 다른 안에서 `이 안 자세히 보기`를 클릭합니다.
2. 하단 상세 영역을 확인합니다.

기대 결과:

- `현재 자세히 보는 안` 요약이 선택한 안으로 바뀝니다.
- grid/proof/off 요청 탭 내용이 그 안 기준으로 바뀝니다.
- `현재 기준안`은 버튼을 누르지 않은 이상 그대로 유지됩니다.

### 시나리오 F. `이 안을 기준안으로 사용`이 공식 후보만 바꾸는지 확인

대상 fixture: `BASE-MULTI`

실행:

1. 현재 기준안이 아닌 카드에서 `이 안을 기준안으로 사용`을 클릭합니다.
2. 상단 요약을 확인합니다.

기대 결과:

- `현재 기준안`이 해당 안으로 바뀝니다.
- 선택한 안 카드에 `현재 기준안` 배지가 붙습니다.
- `현재 자세히 보는 안`은 별도 보기 전환을 하지 않았다면 그대로일 수 있습니다.

### 시나리오 G. 비교 워크스페이스가 차이를 문장으로 먼저 보여주는지 확인

대상 fixture: `BASE-MULTI`

실행:

1. 상태나 입력 차이가 있는 두 안을 비교에 올립니다.
2. 워크스페이스의 `핵심 차이` 영역을 봅니다.

기대 결과:

- 단순 상태명만 나오는 것이 아니라 차이를 문장으로 요약합니다.
- 예:
  - `V2안의 Off 요청 반영률이 더 높습니다.`
  - `V2안은 바로 확정할 수 있습니다.`
  - `V3안은 직접 수정이 있어 다시 검사가 필요합니다.`

### 시나리오 H. 상태별 기본 패널이 올바른지 확인

대상 fixture: `READY`, `PENDING`, `BLOCKED`, `INFEASIBLE`, `FAILED`, `FINALIZED`

| fixture      | 첫 화면에서 먼저 보여야 하는 것 |
| ------------ | ------------------------------- |
| `READY`      | grid 중심 화면                  |
| `PENDING`    | `재검토 필요` 패널              |
| `BLOCKED`    | `하드 제약 위반 요약` 패널      |
| `INFEASIBLE` | `생성 불가` 패널                |
| `FAILED`     | `생성 실패` 패널                |
| `FINALIZED`  | grid 중심 + 읽기 전용 상태      |

실행:

1. 각 fixture를 하나씩 엽니다.
2. `현재 자세히 보는 안` 아래의 상세 패널을 확인합니다.

기대 결과:

- 각 상태에 맞는 패널이 먼저 열립니다.
- finalized가 아니면 비교 도구를 접거나 펼칠 수 있습니다.
- finalized면 비교 도구가 보이지 않습니다.

### 시나리오 I. `수정 후 다시 검사 필요 -> 다시 검사 -> 확정 가능` 흐름 확인

대상 fixture: `PENDING`

실행:

1. `재검토 필요` 안내가 보이는지 확인합니다.
2. primary action 버튼이 `다시 검사`인지 확인합니다.
3. 버튼을 클릭합니다.

기대 결과:

- pending 안내가 사라지거나 약해집니다.
- 상태가 `확정 가능` 또는 현재 데이터에 맞는 다음 정상 상태로 바뀝니다.
- primary action도 그 상태에 맞게 갱신됩니다.

### 시나리오 J. `확정 가능 -> 최종 확정` 흐름 확인

대상 fixture: `READY`

실행:

1. `현재 기준안`이면서 `확정 가능` 상태인 안을 확인합니다.
2. primary action 버튼이 `이 안으로 최종 확정`인지 확인합니다.
3. 버튼을 클릭합니다.
4. 새로고침합니다.

기대 결과:

- 해당 안에 `최종 확정됨` 표시가 보입니다.
- 읽기 전용 안내가 보입니다.
- grid가 편집되지 않습니다.

### 시나리오 K. `생성 중 오류 발생`에서는 `다시 생성`이 primary인지 확인

대상 fixture: `FAILED`

실행:

1. `생성 실패` 패널이 먼저 보이는지 확인합니다.
2. `Trace ID`가 보이는지 확인합니다.
3. primary action 버튼 라벨을 확인합니다.

기대 결과:

- `생성 실패` 패널이 먼저 보입니다.
- 실패 이유 또는 요약이 보입니다.
- 가능하면 `Trace ID`가 보입니다.
- primary action은 `다시 생성` 1개만 강하게 보입니다.

### 시나리오 L. finalized 상태에서는 비교 도구가 숨겨지고 편집이 막히는지 확인

대상 fixture: `FINALIZED`

실행:

1. `FINALIZED` fixture를 엽니다.
2. 상단에 `비교 도구`, `비교 후보`, `비교 워크스페이스`가 있는지 확인합니다.
3. 임의 셀을 수정하려고 시도합니다.

기대 결과:

- 비교 도구가 아예 보이지 않습니다.
- 셀 수정이 되지 않습니다.
- 읽기 전용 안내가 보입니다.

### 시나리오 M. 엑셀 다운로드가 가능한지 확인

대상 fixture: `READY` 또는 `FINALIZED`

실행:

1. Step5 하단에서 `엑셀 다운로드` 버튼을 찾습니다.
2. 버튼을 클릭합니다.

기대 결과:

- 브라우저 다운로드가 시작되거나 저장 동작이 트리거됩니다.
- 화면 오류가 발생하지 않습니다.

### 시나리오 N. finalized 월은 Step3에서 직원 재저장이 차단되는지 확인

대상 fixture: `FINALIZED`

실행:

1. 대시보드로 돌아갑니다.
2. `FINALIZED` 카드의 `수정` 버튼을 클릭합니다.
3. Step1, Step2를 통과한 뒤 Step3에서 `저장`을 클릭합니다.

기대 결과:

- 아래 에러 메시지가 보입니다.  
  `현재 월에 확정된 근무표가 있어 직원 정보를 다시 저장할 수 없습니다.`
- 직원 재생성 흐름이 진행되지 않습니다.
- 파괴적 확인창이 뜨지 않습니다.
