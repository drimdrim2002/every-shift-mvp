# P5-1.3: Organization / Settings API Contracts

## Decision Summary

Phase 5 fixes the organization-management persistence boundary as:

- Canonical transport: direct Supabase `.from('<table>')`
- Canonical protection: route guard + client scope rules + database RLS
- Not canonical for P5: RPC-only write path, custom server function, cross-table
  transaction wrapper

If later work introduces cross-table invariants that cannot be expressed safely
through independent table writes, that later task may add a server boundary.
That is not the Phase 5 baseline.

## Tables Covered

- `organizations`
- `organization_settings`

This task does not redefine the contracts for `sites`, `skills`, `ranks`, or
`site_staffing_requirements`, but those modules should continue following the
same API-layer pattern.

## Why Direct `.from()` Is Canonical

Current code already uses client-side API modules under `src/api/**` with:

- local row interfaces (`snake_case`)
- row-to-domain mappers (`camelCase`)
- explicit CRUD helpers
- Korean error messages at the boundary

That pattern is already used by `shift.ts`, `site.ts`, `skill.ts`, `rank.ts`,
and `organization-settings.ts`. Phase 5 aligns `organization.ts` to the same
contract instead of introducing a competing RPC convention.

## Access and Scope Contract

### Allowed UI callers

| Access state   | Page access | API intent allowed | Organization scope |
| -------------- | ----------- | ------------------ | ------------------ |
| `super_active` | Yes         | Yes                | Selected org       |
| `admin_active` | Yes         | Yes                | Own org only       |
| `user_active`  | No          | No                 | None               |
| blocked/other  | No          | No                 | None               |

### Client rule

The organization-management UI must pass an explicit scope object:

```typescript
interface OrganizationManagementScope {
  accessState: AccessState | null;
  organizationId: string | null;
}
```

- `super_active`
  - may list all organizations
  - must choose a target organization before loading detail or saving
- `admin_active`
  - may not switch organization context
  - target organization must equal `effectiveMembership.organizationId`
- `user_active`
  - must not render the page
  - must not call organization-management API helpers

### Server rule

The client scope helper is a UX and guard rail only. Real tenant isolation must
still be enforced by RLS:

- super: allowed to read/write all organization rows according to elevated
  policy
- admin: allowed to read/write only rows for the approved membership
  organization
- user: denied

## Organization Type Contract

Application types still expose:

```typescript
type OrganizationType = 'hospital' | 'fire' | 'police' | 'logistics' | 'production';
```

But Phase 5 save operations are intentionally narrower:

```typescript
const PERSISTED_ORGANIZATION_TYPES = ['hospital', 'fire', 'police'] as const;
```

Phase 5 forms and API writes must use only the DB-safe subset until a schema
change expands database support.

## Canonical API Signatures

### `src/api/organization.ts`

```typescript
loadOrganization(orgId: string): Promise<Organization>
loadAllOrganizations(): Promise<Organization[]>

loadOrganizationsForManagement(
  scope: OrganizationManagementScope,
): Promise<Organization[]>

loadOrganizationForManagement(
  scope: OrganizationManagementScope,
  targetOrganizationId?: string | null,
): Promise<Organization>

saveOrganizationForManagement(
  scope: OrganizationManagementScope,
  orgData: OrganizationProfilePatch,
  targetOrganizationId?: string | null,
): Promise<Organization>
```

Supporting types:

```typescript
interface OrganizationProfileInput {
  name: string;
  type: PersistedOrganizationType;
}

interface OrganizationProfilePatch {
  name?: string;
  type?: PersistedOrganizationType;
}
```

Notes:

- `saveOrganizationForManagement()` is the Phase 5 page-level write contract
- root organization create/delete are not part of the `/admin/organization`
  page contract even if lower-level helpers still exist elsewhere
- `resolveOrganizationManagementOrganizationId()` enforces super/admin client
  scope before the query runs

### `src/api/organization-settings.ts`

```typescript
loadSettings(orgId: string): Promise<OrganizationSettings | null>
upsertSettings(
  orgId: string,
  settings: OrganizationSettingsSaveInput,
): Promise<OrganizationSettings>

loadSettingsForManagement(
  scope: OrganizationManagementScope,
  targetOrganizationId?: string | null,
): Promise<OrganizationSettings | null>

saveSettingsForManagement(
  scope: OrganizationManagementScope,
  settings: OrganizationSettingsSaveInput,
  targetOrganizationId?: string | null,
): Promise<OrganizationSettings>
```

Supporting type:

```typescript
type OrganizationSettingsSaveInput = Partial<
  Pick<OrganizationSettings, 'maxConsecutiveNightShifts' | 'minimumRestHours' | 'workConstraints'>
>;
```

Notes:

- `organization_settings` stays a one-row-per-organization table
- canonical write remains `upsert(..., { onConflict: 'organization_id' })`
- missing settings row is valid on read and returns `null`

## Error Contract

- Permission/scope mismatch at client boundary
  - `조직 관리 권한이 없습니다.`
  - `슈퍼 관리자는 대상 조직을 선택해야 합니다.`
  - `관리자 조직 범위를 확인할 수 없습니다.`
  - `다른 조직 데이터에는 접근할 수 없습니다.`
- Supabase errors stay normalized to Korean feature messages
  - `조직 조회 실패: ...`
  - `조직 수정 실패: ...`
  - `설정 조회 실패: ...`
  - `설정 저장 실패: ...`

Frontend branching should still prefer structured scope/access checks where
available rather than parsing free-form message text.
