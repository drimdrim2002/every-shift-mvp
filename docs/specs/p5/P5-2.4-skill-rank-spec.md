# P5-2.4: Skill & Rank Master Canonical Specification

## Purpose

This document fixes the Phase 5 contract for organization-level skill and rank
master data. It resolves four recurring ambiguities in the current backlog and
implementation notes:

1. Canonical table names are `skills` and `ranks`, not legacy
   `organization_skills` / `organization_ranks`.
2. Phase 5 delete UX is blocked-first even though the current DB uses
   `CASCADE` / `SET NULL` in some paths.
3. New-organization defaults are `GENERAL` for skill and `RN` for rank.
   `LV1~LV4` remain examples, not mandatory seed rows.
4. `rank.credit` is optional in Phase 5 but becomes the initial suggested
   employee credit in Phase 6.

## Scope

In scope:

- `skills`
- `ranks`
- `src/api/skill.ts`
- `src/api/rank.ts`
- Admin master-data UI copy and validation rules
- Downstream assumptions for `P5-2.5` and `P5-3.1`

Out of scope:

- Employee schema expansion in P6
- DB migration to change FK delete actions to `RESTRICT`
- Soft delete schema design

## Canonical Schema Contract

### Skill

Primary table: `public.skills`

| Column          | Type         | Nullable | Contract               |
| --------------- | ------------ | -------- | ---------------------- |
| id              | UUID PK      | NO       | `gen_random_uuid()`    |
| organization_id | UUID FK      | NO       | org-scoped master row  |
| code            | VARCHAR(50)  | NO       | normalized unique code |
| name            | VARCHAR(100) | NO       | display label          |
| created_at      | TIMESTAMPTZ  | NO       | `DEFAULT NOW()`        |

DB basis: `UNIQUE (organization_id, code)`

### Rank

Primary table: `public.ranks`

| Column          | Type           | Nullable | Contract                      |
| --------------- | -------------- | -------- | ----------------------------- |
| id              | UUID PK        | NO       | `gen_random_uuid()`           |
| organization_id | UUID FK        | NO       | org-scoped master row         |
| code            | VARCHAR(50)    | NO       | normalized unique code        |
| name            | VARCHAR(100)   | NO       | display label                 |
| credit          | NUMERIC(10, 2) | YES      | optional numeric weight/value |
| created_at      | TIMESTAMPTZ    | NO       | `DEFAULT NOW()`               |

`credit` is added by migration 012 and remains nullable in Phase 5.

## Validation Rules

### Shared `code` rules

- Input is trimmed before validation.
- Stored value is normalized to uppercase before persistence.
- Uniqueness is organization-scoped and evaluated on the normalized value.
- Maximum length is 50 characters.
- Empty string is invalid.

Recommended UI/API error message:

- Create/update duplicate: `이미 존재하는 코드입니다.`

### `name` rules

- Required
- Maximum length is 100 characters

### `credit` rules

- Optional in Phase 5
- If provided, it must be a finite numeric value `>= 0`
- Display format uses two decimal places in list/detail UI
- Blank input is stored as `NULL`

## Default Data Policy

When a new organization is initialized, Phase 5 assumes the following minimal
default master rows:

- Skill: `GENERAL`
- Rank: `RN`

These are the canonical seed defaults for admin UX and empty-state examples.

### PRD examples versus seed defaults

The PRD references `LV1`, `LV2`, `LV3`, `LV4` as valid operating examples for
rank configuration. In Phase 5, those values are treated as optional
organization-defined rows, not mandatory bootstrap data.

Decision:

- Seed default: `RN`
- Example operational extension: `LV1~LV4`

This distinction prevents the admin shell, migration backfill, and employee
creation flow from assuming a larger seed set than the database currently
guarantees.

## Credit Semantics

`rank.credit` does not force a credit model in Phase 5 scheduling behavior.
Instead, it establishes a reusable organization master value for later flows.

Phase 5 contract:

- Rank credit may be absent (`NULL`)
- Admins can view and edit credit as part of rank management
- Credit formatting is present even if downstream employee logic is not yet
  implemented

Phase 6 handoff contract:

- When a new employee is created and a rank is selected, `rank.credit` is used
  as the initial suggested employee credit value
- The employee-level stored credit is a separate value and may diverge from the
  current rank default after assignment

## Delete and Referential Integrity Contract

### Desired Phase 5 UX contract

Phase 5 uses a blocked-first delete policy:

- If a skill or rank is in use, the UI should stop deletion and explain why
- The user should be guided to remove dependent usage first
- The UI must not rely on silent cascades or silent nulling as acceptable
  product behavior

### Current database reality

The current schema does not fully enforce the desired product behavior:

| Reference path                          | Current FK behavior  | Desired Phase 5 UX  |
| --------------------------------------- | -------------------- | ------------------- |
| `employee_skills.skill_id -> skills.id` | `ON DELETE CASCADE`  | Block before delete |
| `site_staffing_requirements.skill_id`   | `ON DELETE SET NULL` | Block before delete |
| `site_staffing_requirements.rank_id`    | `ON DELETE SET NULL` | Block before delete |

This is a known delta between schema behavior and product contract.

### Canonical implementation decision for P5

P5 does not require an immediate FK migration to `RESTRICT`.
The default implementation path is:

1. Keep current schema unchanged in P5-2.4.
2. Add pre-delete reference checks in the application/service layer.
3. Show a user-facing blocked message when references exist.
4. Record DB-enforced `RESTRICT` migration as a follow-up hardening candidate.

This keeps Phase 5 implementation small while preserving the product contract.

### Current reference scope

Skill delete checks must consider:

- `employee_skills`
- `site_staffing_requirements`

Rank delete checks must consider:

- `site_staffing_requirements`

Employee-to-rank direct FK checks are not part of current Phase 5 schema and
must not be documented as an already-existing DB constraint. That becomes a
Phase 6 schema concern.

## UI Contract

Target route: `/admin/organization`

Target surfaces:

- `OrganizationManagement.vue` tab `스킬`
- `OrganizationManagement.vue` tab `직급`

### Skill tab requirements

- Columns: `code`, `name`, `actions`
- Empty-state/example row should align with `GENERAL`
- Delete CTA must describe blocked-first behavior

### Rank tab requirements

- Columns: `code`, `name`, `credit`, `actions`
- Empty-state/example row should align with `RN`
- Credit cell displays `-` when null, formatted decimal when present

## API Alignment Notes

Current APIs already upper-case codes before persistence:

- `src/api/skill.ts`
- `src/api/rank.ts`

However, current delete handlers assume the DB will raise `23503` for in-use
records. That assumption is incomplete under the live FK configuration above.

Required interpretation:

- Duplicate handling is already aligned with the spec
- Delete handling needs preflight reference checks before calling `.delete()`
- User-facing copy should describe the blocked-first policy, not DB-only
  behavior
