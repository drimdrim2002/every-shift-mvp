## Tenant Isolation Scenarios

1. **Admin A requests Org B's settings**: RLS `has_org_access(org_id, 'admin')` returns false -> empty result or permission denied.
2. **Malicious `organization_id` in POST body**: client scope and RLS both reject cross-org write attempts.
3. **Super reads all orgs**: `is_super_admin()` -> true -> bypasses org filter.
4. **Pending admin tries admin page**: `accessState === 'admin_pending'` -> router redirects to `/access/pending`.
5. **Rejected admin tries admin page**: `accessState === 'admin_rejected'` -> router redirects to `/access/rejected`.
6. **User tries admin page directly**: `allowedAccessStates` mismatch -> redirect to `/schedule/step1`.

## Boundary Scenarios

- Saving organization-management data must not update legacy `site_requirements`.
- Phase 5 staffing editors target `site_staffing_requirements` only.
- No dual-write or auto-sync path exists between the two staffing tables.

## Delete Policy Scenarios

- UI treats delete as blocked-first across organization-management master data.
- If a record is in use, the preferred result is a blocked action with an explanatory Korean message.
- Current DB `CASCADE` / `SET NULL` behavior is tracked as schema delta and must not be treated as desired UX.

## Downstream CRUD Validation Scenarios

### Shifts

- Valid data → created, appears in list
- Duplicate `code` → error: "이미 존재하는 시프트 코드입니다"
- FK reference exists → delete blocked with Korean message
- Code with lowercase input → auto-uppercased before save

### Sites

- Same CRUD pattern as shifts
- Delete blocked if `site_staffing_requirements` or `employee_site_assignments` reference exists

### Skills / Ranks

- Duplicate code → 23505 error → Korean message
- Delete blocked if referenced in `employee_skills` / `site_staffing_requirements`
