# P5-1.1: Organization Management Canonical Contract

## Purpose

This document is the canonical contract for Phase 5 organization management.
Downstream tasks (`P5-1.2`, `P5-1.3`, `P5-1.4`) must follow this document instead
of older migration-era notes that still reference `meta.roles` or
`/admin/organizations`.

## Canonical Route and Access Contract

### Route

- Canonical route: `/admin/organization`
- Page shape: single page shell with tabs
- Older `/admin/organizations` references are legacy only and must not be used
  as the Phase 5 implementation target.

### Frontend guard contract

Use the app's current router convention:

```typescript
meta: {
  title: '조직 관리',
  requiresAuth: true,
  allowedAccessStates: ['super_active', 'admin_active'],
}
```

Do not introduce a parallel `meta.roles` contract for this feature.

### Access-state behavior

| Access state      | Menu visible | Direct route access                               | Organization scope    |
| ----------------- | ------------ | ------------------------------------------------- | --------------------- |
| `super_active`    | Yes          | Allowed                                           | Any organization      |
| `admin_active`    | Yes          | Allowed                                           | Own organization only |
| `admin_pending`   | No           | Redirect to `/access/pending`                     | None                  |
| `admin_rejected`  | No           | Redirect to `/access/rejected`                    | None                  |
| `user_active`     | No           | Redirect to post-auth default (`/schedule/step1`) | None                  |
| `unauthenticated` | No           | Redirect to `/login`                              | None                  |

## Scope Boundary

### In scope for the Phase 5 organization management screen

- `organizations`
- `organization_settings`
- `site_staffing_requirements` (service-native staffing requirements)
- Related master data tabs handled by downstream P5 tasks

### Explicitly out of scope for P5-1.1

- Runtime implementation of the screen itself
- Database migrations
- RLS changes
- Any automatic sync between legacy `site_requirements` and
  `site_staffing_requirements`

### Legacy vs service-native staffing boundary

| Table                        | Owner in P5            | Role in product                | Rule                                       |
| ---------------------------- | ---------------------- | ------------------------------ | ------------------------------------------ |
| `site_requirements`          | Schedule wizard Step 2 | Legacy MVP staffing input      | Keep untouched in Phase 5                  |
| `site_staffing_requirements` | Organization admin UI  | Service-native staffing source | Phase 5 admin screen edits this table only |

> **Decision**: Phase 5 must not dual-write or auto-sync the two tables. The
> migration from wizard legacy data to service-native staffing remains a later
> phase concern.

## Data Model

### `organizations`

This remains the root organization entity. Phase 5 does not add new columns to
this table.

| Column     | Type        | Nullable | Notes                    |
| ---------- | ----------- | -------- | ------------------------ |
| id         | UUID PK     | NO       | `gen_random_uuid()`      |
| name       | VARCHAR     | NO       | Display name             |
| type       | VARCHAR(20) | NO       | See allowed values below |
| created_at | TIMESTAMPTZ | NO       | `DEFAULT NOW()`          |
| updated_at | TIMESTAMPTZ | NO       | `DEFAULT NOW()`          |

> **Decision**: Extended work-rule fields do not belong on `organizations`.
> They belong on `organization_settings`.

### `organization_settings`

This is the only canonical location for organization-level work constraints in
Phase 5.

| Column                       | Type        | Nullable | Default               | Notes                     |
| ---------------------------- | ----------- | -------- | --------------------- | ------------------------- |
| id                           | UUID PK     | NO       | `gen_random_uuid()`   |                           |
| organization_id              | UUID FK     | NO       | UNIQUE                | `-> organizations.id`     |
| max_consecutive_night_shifts | INTEGER     | YES      | `NULL`                | `NULL` means no limit     |
| minimum_rest_hours           | JSONB       | NO       | `{}`                  | Shift code -> hours       |
| work_constraints             | JSONB       | NO       | migration 012 default | Weekly hour/off-day rules |
| created_at                   | TIMESTAMPTZ | NO       | `NOW()`               |                           |
| updated_at                   | TIMESTAMPTZ | NO       | `NOW()`               |                           |

#### `work_constraints` JSONB shape

```json
{
  "weeklyTargetHours": 40,
  "weeklyMaxHours": 52,
  "weeklyOffDays": 2
}
```

#### `minimum_rest_hours` JSONB shape

```json
{ "D": 24, "E": 24, "N": 36 }
```

## Organization Type Contract

Current TypeScript code defines:

```typescript
type OrganizationType = 'hospital' | 'fire' | 'police' | 'logistics' | 'production';
```

However, current DB-safe behavior is narrower:

- Safe persisted values in Phase 5 UI: `hospital`, `fire`, `police`
- Reserved future values: `logistics`, `production`

> **Decision**: Phase 5 forms, selects, and API payloads must be limited to the
> DB-supported subset until a dedicated schema migration expands the allowed DB
> values. The broader TypeScript union is a known compatibility delta, not a
> license to expose unsupported values in the UI.

## Role and UX Contract

### Super admin

- Can open the page for any organization
- Sees a single-select organization dropdown at the top of the page
- Can switch the active organization context one at a time
- Downstream save calls must target the selected organization only

### Admin

- Opens the same route and same page shell
- Does not see an organization selector
- Is always scoped to the effective membership organization

### User

- Must not see the menu item
- Must not access the route directly
- Must not call organization-management APIs from the UI

## Operation Contract

### Page-level capability in Phase 5

| Operation                              | `super_active` | `admin_active` | Notes                                  |
| -------------------------------------- | -------------- | -------------- | -------------------------------------- |
| View organization info                 | Yes            | Yes            | admin is own-org only                  |
| Update organization name/type          | Yes            | Yes            | type options limited to DB-safe subset |
| View/update `organization_settings`    | Yes            | Yes            | own-org only for admin                 |
| View/edit `site_staffing_requirements` | Yes            | Yes            | handled in downstream P5 tasks         |

### Deferred root-entity operations

| Operation                | Decision                                                        |
| ------------------------ | --------------------------------------------------------------- |
| Create organization root | Not part of the `/admin/organization` Phase 5 shell             |
| Delete organization root | Out of scope for Phase 5 UI; do not assume a public delete flow |

## Delete Policy

Phase 5 adopts a **blocked-first** delete policy across organization-management
master data.

This means:

- The UI must not assume silent cascade deletion is acceptable behavior.
- If an entity is in use, the preferred UX is to block delete and explain why.
- Existing DB FK behavior (`CASCADE` / `SET NULL`) is a current-schema delta and
  must be treated as an implementation risk, not the desired user contract.

Examples:

- Site deletion should not be designed as "delete and let staffing rows cascade"
- Skill or rank deletion should not be designed as "delete and let references
  null out"
- Root organization deletion is excluded from the Phase 5 UI contract entirely
